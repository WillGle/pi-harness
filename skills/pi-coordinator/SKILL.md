# Coordinator doctrine

Keep Mission reasoning separate from execution. Main Pi is the Commander and holds the Mission objective, Constraints, Definition of Done (DoD), important Decisions, major Blockers, and Mission status. Harness runs a separate Coordinator context for every Operation. Main Pi receives only a bounded OperationReport or a safe Operation handoff status. It must not receive a TaskResult or raw Evidence. Only the Harness Coordinator can dispatch, accept, reject, or judge TaskResults in an Operation. No child may spawn another child.

## Order before dispatch

For each Operation, register only the objective, allowed Harness execution-policy IDs, shared Constraints, and Operation Acceptance Criteria with `pi_harness_operation`. Do not register TaskOrder IDs, task intents, Dependencies, TaskSpecs, permissions, or verification commands. Call `pi_harness_run_operation` to hand control to the Harness Coordinator. The Coordinator must first return `plan_tasks` semantic proposals with `local_ref`, role, scope, Dependencies by `local_ref`, Task Acceptance Criteria, and an allowed execution-policy ID. Harness validates the complete plan, assigns TaskOrder IDs, resolves trusted TaskSpecs, and materializes the TaskGraph atomically before dispatch. Every read-only TaskOrder must include at least one specific Acceptance Criterion; Harness rejects it otherwise. `owner` values are `scout`, `research`, or `worker`; these are role profiles, not separate orchestration runtimes. The legacy `pi_harness_coordinate` tool remains as a disabled compatibility stub. Do not use it to spawn a child or promote a TaskResult.

The Coordinator proposes one CoordinatorDecision per turn. Harness validates the decision and alone dispatches through pi-subagents. The Commander must not accept or reject individual TaskResults. In `/plan on`, do not start or resume an Operation. Read-only profiles cannot mutate; write Workers use isolated worktrees. The package creates the atomic Worker commit with policy metadata. Never merge or integrate automatically; obtain explicit user confirmation before integration.

## Close the loop

Separate execution from acceptance. A child reporting completion is not Definition of Done. For Workers, Harness runs the named deterministic gate in the worktree and checks the package branch and single commit. The deterministic Verifier checks gate execution, gate result, branch and single-commit policy after execution. If semantic Acceptance Criteria remain, Harness sends selected bounded Evidence to the read-only `reviewer` profile. Harness validates the structured result before it can change Verification Status. If the Verifier cannot check a criterion, the TaskResult remains blocked. Harness rejects a read-only TaskOrder in an Operation unless it has explicit Acceptance Criteria. Read-only child prose is not an independently verified fact. Retry, replan, or escalate Blockers; report only accepted conclusions upward.

Promote a versioned **TaskResult** to the Coordinator, not a transcript. The TaskResult has separate Execution Status and Verification Status, a bounded semantic summary, changed paths, and Evidence/Artifact references. Harness stores bounded raw execution data outside the repository. Only the Harness Verifier reads selected Evidence. For read-only TaskOrders, the Verifier checks each explicit Acceptance Criterion and promotes only evidence-backed findings. The Coordinator receives those structured findings, not the child prose. The Commander receives only a bounded OperationReport. Legacy `success` is a combined lifecycle/gate/commit check, not acceptance. Do not interpret it as Definition of Done. Do not copy raw payloads into plans, memory, or compaction state.

The Coordinator proposes TaskResult and Operation Acceptance Criterion decisions. Harness validates them and applies each transition after Dependencies and Evidence checks. Commander-facing Operation status contains no TaskResult or Evidence content. Operation completion does not complete the Mission. Goal cancellation flows through Harness to active package tasks, including the semantic Verifier. Integration and Mission completion remain explicit decisions of the Commander; child results alone do not close a Mission.
