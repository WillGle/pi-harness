# Pi Harness Architecture

## Scope

Pi Harness is a Pi package for Pi `0.85.1`; it does not replace Pi, select a provider/model, create a separate GUI, or train a model. Provider, model, and authentication remain machine-local Pi choices.

## Package layout

```text
pi-harness/
├── extensions/pi-harness.ts       # Harness commands and tools
├── lib/state.mjs                  # persisted-state and safety contracts
├── lib/coordinator.mjs            # Harness-only pi-subagents dispatch adapter
├── lib/operation-runner.mjs       # bounded Coordinator state and serial control loop
├── lib/task-graph.mjs             # persistent TaskGraph and deterministic Scheduler
├── lib/communication.mjs          # L2 TaskOrder/TaskResult contract and promotion
├── lib/evidence.mjs               # local bounded Evidence Store and integrity-checked retrieval
├── lib/verifier.mjs               # Harness-owned deterministic acceptance checks
├── lib/semantic-verifier.mjs      # bounded VerificationOrder and checked semantic result
├── lib/operation.mjs              # session-scoped Coordinator acceptance state
├── lib/worker-gate.mjs            # Harness-specific verification and result policy
├── lib/memory.mjs                 # explicit /learn project memory
├── lib/precise-edit.mjs           # bounded hashline editing
├── lib/code-intel.mjs             # bounded code intelligence
├── bin/pi-harness*.mjs            # doctor and bounded web CLI
├── skills/                        # curated, locked Pi skills
└── packages/pi-harness-acp/       # ACP stdio bridge
```

`package.json` declares Pi extensions, skills, executable commands, and the pinned `@tintinweb/pi-subagents@0.19.0` dependency. It has no project prompt resource. `.pi/subagents.json` sets serial-safe package limits and explicit worktree isolation. `scripts/bootstrap.mjs` checks Node/Pi and installs this package through `pi install`; it must not modify Pi provider, model, or authentication settings.

## Session behavior

The extension persists `pi-harness-plan-state`, `pi-harness-goal-state`, `pi-harness-operation-state`, `pi-harness-coordinator-state`, and `pi-harness-task-graph-state` custom session entries. The newest TaskGraph entry includes its owning Operations as one atomic Scheduler snapshot; it takes precedence over older legacy Operation entries during restore. It also checkpoints before Pi-native and Harness proactive compaction. Session reload reconciles an interrupted `running` claim into an explicit Scheduler Blocker, never a ghost running Task. The model does not own this state.

- `/plan on` removes `edit` and `write` from active tools. In plan mode, bash is limited to classified read-only commands and the agent receives a planning prompt requiring assumptions, numbered steps, and verification criteria.
- `/plan off` restores tools captured before plan mode. `/plan status` reports state.
- `/goal <objective>` creates one active goal only when plan mode is off. `/goal status` reports it; `/goal cancel` records cancellation. Terminal completion/blocking must carry evidence.

The current implementation persists and enforces these command contracts. The lifecycle tests prove persisted reload, real compaction, real fork/branch independence, and mutation blocking after lifecycle transitions. The goal intentionally does not own wait state, pause/resume, token budgets, or a strong no-progress circuit breaker.

## Coordination boundary

Every delegated task needs an owner, scope, verification command, and permission. `@tintinweb/pi-subagents` owns child sessions, tool restrictions, queues, concurrency, cancellation, and worktrees. Harness agent definitions keep scouts/researchers read-only and workers write-capable. Harness runs the worker gate and commit policy, captures bounded evidence, links goal cancellation, and leaves branch integration as a separate, explicit user-confirmed action. No worker may edit the coordinator worktree.

## Communication contract (foundation shipped; full coordination is not)

Canonical control-plane language is **ASD-STE100-derived Agent English**. This uses ASD-STE100 principles only; no certified ASD-STE100 compliance or full parser is claimed. Compress redundancy, not control semantics. Use one term per concept and one meaning per term. Use short sentences, one main fact per sentence, active voice when practical and an explicit actor. Put conditions before dependent actions. Preserve `if`, `only if`, `unless`, `before`, `after`, `because`, `while`, `until`, `must`, `must not`, `may`, `cannot`, `requires`, `depends on`, negation and exceptions. Keep identifiers exact. State uncertainty and status explicitly. Do not infer verification from execution completion.

| Layer | Contract |
|---|---|
| L0 Commander | Controlled Technical English. Only Mission, Constraints, Definition of Done, important Decisions, major Blockers and Mission status. No raw Worker logs, diffs, shell output, retries or receipts. |
| L1 Coordinator | Concise Controlled Technical English. Operation and TaskOrder state, Dependencies, accepted TaskResults, retry/replan decisions, escalation and Blockers. No raw L3 context by default. |
| L2 TaskOrder / TaskResult | Versioned schema plus Controlled Technical English in semantic fields. Harness formats TaskOrders and projects TaskResults before the parent tool response. |
| L3 Worker / ExecutionUnit | Normal technical language. Source, debugging, commands, retries and raw test output are disposable and do not automatically propagate. |
| Evidence / Artifact | Harness stores bounded raw execution data outside the repository. TaskResult carries references only. A worker branch remains an Artifact, not Evidence. |
| Caveman | Optional human-requested presentation or L3 compact execution receipt only. A receipt is not a TaskResult. It cannot rewrite L0/L1/L2 semantics. |

Canonical terms: Mission (L0 objective), Operation (coordinated work), TaskOrder (dispatch contract), TaskResult (promoted semantic result), ExecutionUnit (package child), Commander (L0 decision maker), Coordinator (L1 decision maker), Worker (write-capable execution profile), Verifier (acceptance checker), Constraint (limit), Acceptance Criterion (required check), Dependency (required prior state), Blocker (blocked action and condition needed to resume), Evidence (raw observation), Artifact (produced output), Execution Status (execution lifecycle), Verification Status (acceptance checks). Avoid synonyms such as job, ticket, assignment, work item, request and work order for TaskOrder.

Status vocabulary: `assigned` means the Coordinator assigned the TaskOrder; `running` means the ExecutionUnit is executing it; `execution_complete` means normal termination with an execution result, **not** verification; `verifying` means the Verifier is checking Acceptance Criteria; `verified` means all required Acceptance Criteria passed; `failed` means execution or verification failed; `blocked` means a stated Blocker prevents progress; `complete` means the parent Operation accepted a verified TaskResult. `not_verified` explicitly means no complete acceptance check has occurred. Do not interchange these statuses. Harness now runs a deterministic Verifier after the ExecutionUnit stops. The Worker gate still runs before worktree cleanup. If the Worker completed, the gate ran and passed, the package branch exists, the commit policy is valid, exactly one commit exists, Evidence persistence succeeded, and no additional Acceptance Criteria require semantic review, the Verifier returns `verified`. If any required deterministic check fails, it returns `failed`. If additional semantic Acceptance Criteria remain, it returns `not_verified` with a verification summary. Scout and research remain `not_verified` when they complete without checked semantic Acceptance Criteria. Harness does not yet persist a `verifying` state. Operation acceptance is a separate Coordinator action. The legacy `success` property in internal records is not a Verification Status.

TaskOrder v1 accepts the flat legacy fields and optional `task_id`, `operation_id`, `constraints`, `acceptance_criteria`, and per-criterion `review_evidence` kind selection. Harness generates an ID when absent and formats actor, objective, conditions, Constraints, Acceptance Criteria and verification without paraphrasing caller text. TaskResult v1 includes `task_id`, `execution_status`, `verification_status`, deterministic summary, changed paths and available branch Artifact reference. The Coordinator does not promote child prose as a semantic summary: it cannot safely infer child claims from untrusted prose. The tool does not return raw Evidence; direct internal callers can still access the legacy bounded record during migration. Evidence references now identify persisted raw execution material. The deterministic Verifier adds a semantic verification summary. If Evidence persistence fails, the TaskResult reports the failure and cannot be `verified`. Cavecrew is only a reporting profile; Pi Harness owns dispatch and lifecycle through `pi_harness_coordinate`. Pi owns provider/model/session/compaction and pi-subagents owns child lifecycle/worktrees. Harness may request proactive compaction only after a settled idle boundary: `/harness-compact set <50-90>|status|disable` persists `enabled` and `threshold_percent` in a session entry (enabled by default at 70% of the active model's context window; configurable whole-number 50–90%; an explicit disable is persisted). The active model's `getContextUsage().percent` crossing the selected threshold sets a pending flag in `context` without calling `ctx.compact()`. At `agent_settled`, with no active tools, TaskOrders, Reviewer, or managed Operation, Harness checkpoints the control plane and calls Pi's compaction API once; only its completion/error callback permits Goal continuation. After success or failure, re-arm requires usage to fall below the threshold, preventing repeat attempts at the same high-water mark. Session switches clear transient requests and restore the threshold. `session_before_compact` checkpoints state for manual and Pi-native compactions but never schedules them. Pi-native auto-compaction remains the mid-run/emergency fallback; compaction does not decide TaskOrder, Operation, or Mission status. The control contract is enforced by Harness code and prompts, not optional skill selection.

## Shipped Evidence and Verifier pipeline

`Commander -> Coordinator -> TaskOrder -> ExecutionUnit -> Evidence Store -> deterministic Verifier -> optional semantic Verifier -> TaskResult -> Coordinator accepts -> Operation -> Commander evaluates Mission Definition of Done`. Operation `complete` does not set Mission `complete`. Harness persists bounded Worker execution result, gate output and diff, and read-only scout/research report before it constructs the TaskResult. Empty output is not invented; an executed gate with empty output is still stored. The parent tool response contains semantic TaskResult fields and references, not raw logs, diffs, or reports. Direct internal callers retain legacy bounded raw fields during migration. The Verifier evaluates captured gate and package commit checks after execution; it never accepts a Worker claim or legacy `success` as authority.

The file-backed Evidence Store defaults to `~/.pi-harness/evidence/<project-identity>/`, separately from `/learn` memory. `PI_HARNESS_EVIDENCE_DIR` overrides the absolute store root. An Evidence reference has the form `evidence://<project-identity>/<opaque-UUID>`; a caller-supplied TaskOrder ID never becomes a path component. The internal `readEvidence(reference, cwd)` API checks project identity, regular-file ownership/mode, reference grammar, byte limit and SHA-256 before returning bytes. Storage records TaskOrder ID, kind, byte count, SHA-256, creation time and truncation state in a private metadata file. Created directories use owner-only mode; existing store/project directories must be private. Evidence files use owner-only mode, exclusive creation and no-follow flags; directory symlinks are rejected. The implementation does not include a model-facing retrieval tool. Harness explicitly retrieves selected Evidence for semantic review; it does not supply Evidence Store paths to the Reviewer.

Storage preserves the bytes it receives. The existing bounded capture may already append a visible truncation marker; metadata records that truncation. The synchronous gate capture concatenates stdout and stderr without trimming them. It cannot preserve the interleaving of the two streams. Capture limits remain 8 KB for result/gate and 20 KB for diff; storage also has a 32 KB per-item cap. There is no automated retention or quota across tasks. Local users must manage Evidence retention. Evidence is not encrypted or remotely served. A persistence failure produces no fabricated reference and prevents `verified`; references for items successfully stored before a partial failure may remain. Pi still owns provider/model/session/compaction. Pi-subagents still owns child lifecycle/worktrees. Harness does not auto-integrate branches.

### Semantic Verification and Operation acceptance

If a Worker passes deterministic checks and the TaskOrder has additional semantic Acceptance Criteria, Harness sends a bounded VerificationOrder to the read-only `reviewer` ExecutionUnit. Only four exact Worker criteria are classified as already machine-checked: `The Worker verification command passes.`, `The package-managed branch exists.`, `The Worker commit policy is valid.`, and `The Worker produced exactly one commit.` Unknown text remains semantic; there is no natural-language classifier. The Worker gate command itself is deterministic. A scout or research report needs explicit Acceptance Criteria to trigger review; otherwise its TaskResult remains `not_verified`. The packet contains the exact remaining semantic criterion text, objective, constraints, changed paths, and selected raw Evidence. Harness defaults to Worker diff or read-only report. A TaskOrder can select `diff`, `gate`, or `execution` for a Worker criterion through `review_evidence`; read-only criteria can select `report`. Harness validates the kind and sends only the selected items within a 24 KB packet limit. Harness verifies Evidence integrity before selection, rejects truncated or oversized packets, and never sends the Worker transcript or unrelated Evidence. The Reviewer has read-only tools and is instructed not to browse Evidence files, mutate the repository, spawn children, or accept an Operation. The current tool sandbox does not enforce a filesystem path allowlist; the packet supplies no store paths. Harness stores its bounded raw output as Evidence, validates JSON v1 with a status (`passed`, `failed`, `blocked`, `not_checked`) and Evidence references per criterion, and derives the overall status. Malformed, contradictory, missing, truncated, or unresolved review blocks TaskResult verification. The Reviewer cannot override deterministic failure or Evidence failure. `Finding` v1 has a criterion statement, source role, Verification Status, and selected Evidence references; only verified findings are accepted as facts. The model's semantic judgment is not a formal proof or ASD-STE100 validation.

`pi_harness_operation` creates a small session-persisted Operation with an objective, required TaskOrder IDs, optional Dependencies and Operation Acceptance Criteria. `pi_harness_coordinate` can attach a registered TaskOrder using `operation_id` and `task_id`; Harness records only its semantic TaskResult. The Coordinator must explicitly call `accept_task` for the latest recorded, unrejected, `execution_complete` and `verified` TaskResult whose Dependencies are accepted. The Coordinator may call `reject_task`; a later TaskResult for that TaskOrder supersedes the rejected result. The Coordinator must explicitly call `accept_criterion` with integrity-checked Evidence references from a required TaskOrder for each Operation criterion. The Operation becomes `complete` only after all required TaskResults and Operation criteria are accepted. Its status is not Mission status. Operation-level criterion judgments are explicit Coordinator decisions, not independently semantic-reviewed in this phase. Session entries store Operation state with the TaskGraph. Each registered TaskOrder is subject to the Harness Scheduler; manual compatibility tools cannot bypass its ready set.

**Not shipped:** domain Heads, dynamic TaskGraph expansion, parallel multi-Worker orchestration, Mission-level automatic acceptance, or project intelligence. The Reviewer runs as a package-managed sibling, never as a recursive child.

### Separate Coordinator context (Phase E)

The Commander hands a registered Operation to `pi_harness_run_operation({ operation_id, model? })`. The parent receives only a versioned OperationReport (`operation_id`, `status`, concise summary, accepted/blocked TaskOrder IDs, at most five verified Findings, Blocker, optional strategic escalation, and `commander_action_required`). The report is capped at 24 KB, dropping Findings before exceeding the cap. It does not receive individual TaskResults or Coordinator/Worker/Reviewer transcripts. Main Pi retains manual `pi_harness_coordinate` and `pi_harness_operation` for operations not under autonomous control; Harness rejects direct Operation/TaskResult access for a managed Operation, including status inspection, while preserving manual compatibility tools for other Operations. Operation completion never calls `/goal complete`.

Harness builds an OperationBrief v1 from Operation objective, optional current Mission objective, Scheduler ready/pending/running/result_available/accepted/blocked/exhausted TaskOrder IDs, Dependencies, Operation Acceptance Criteria, and semantic TaskResults. CoordinatorState v1 records only the Operation ID, turn count, last seven concise Decisions, and Blocker. Retry accounting belongs to the TaskGraph, not CoordinatorState. A 16 KB packet cap rejects oversized state. The Coordinator profile `.pi/agents/coordinator.md` has only `read` as a built-in tool; `extensions: false`, `skills: false`, `prompt_mode: replace`. Pi-subagents 0.19.0 parses omitted or `tools: none` as **all built-ins**, so `read` is the narrowest safe declared profile; the Coordinator is instructed not to read files in normal coordination. The profile never receives Evidence Store paths or main session messages.

The Coordinator returns one JSON CoordinatorDecision v1 per turn: `dispatch`, `accept_task`, `reject_task`, `accept_criterion`, `block`, or `report`. Harness checks version, Operation ID, fields, TaskOrder registration, Dependencies, read/write permission, task verification, Evidence refs from accepted TaskResults, and state transitions. A Coordinator Decision cannot invoke tools or spawn a Worker. Harness serially dispatches the registered TaskOrder through pi-subagents, performs existing Evidence/Verifier work, records only the semantic TaskResult, and starts the next Coordinator turn. The Coordinator cannot mark Mission complete or integrate a branch. A strategic `block` states the blocked action and required condition; an optional question becomes a structured `strategic_decision_required` escalation. Routine retry remains inside L1. Each TaskOrder has at most two recorded attempts; a run has at most 12 Coordinator turns. Invalid output, exhausted retries, no executable action, or cancellation returns a blocked OperationReport, not success.

**Coordinator session experiment:** the installed pi-subagents 0.19.0 `spawnTopLevel` removes `resumeSessionFile` from RPC options. Only its internal `@handle` dispatcher may resume a stored child session. Harness cannot safely resume a completed Coordinator via RPC, so it uses bounded CoordinatorState and fresh Coordinator turns. Each Coordinator turn terminates before the next Worker is spawned; the package serial slot is released. The test checks the installed package's RPC sanitizer; Harness does not replay a Coordinator transcript. Session entries restore Operation and Coordinator state on reload; switching sessions aborts an active run and prevents it from persisting into the new session. Goal cancellation aborts the active Coordinator turn or managed Worker/Reviewer through its run signal; `pi_harness_cancel_operation` aborts one active managed run. Other Operation state remains unchanged.

### Persistent TaskGraph and serial Scheduler (Phase F)

`TaskGraph` v1 has `operation_id` and `nodes` keyed by registered TaskOrder ID. Each node stores `task_id`, normalized Dependencies copied from the owning Operation, exact `scheduler_status`, `attempts`, `max_attempts` (2), and an optional structured Blocker (`task_id`, `blocked_action`, `required_condition`). It stores no TaskResult, raw Evidence, Worker/Reviewer transcript, stdout, or diff. The Operation owns accepted Task IDs and TaskResults; every graph validation checks exact accepted-set agreement. Graph creation rejects missing, duplicate, and self Dependencies and uses depth-first visiting/visited sets to reject cycles of any length before the Operation is persisted. No Task IDs or Dependencies can be added or rewritten while it runs.

**Scheduler Status** is distinct from Execution Status, Verification Status and Operation status: `pending` (Dependency not accepted), `ready` (all Dependencies accepted with retry budget), `running` (claimed attempt persisted before spawn), `result_available` (TaskResult recorded; Coordinator must decide), `accepted` (verified TaskResult explicitly accepted), `blocked` (structured Blocker prevents dispatch), and `exhausted` (rejected attempt used the last retry). `readyTaskIds` requires an open Operation, accepted Dependencies, an eligible ready node, remaining attempt budget and no other running claim. The Coordinator receives only bounded Scheduler summary IDs, selects one ready TaskOrder, and cannot mutate readiness. Harness validates the proposed ID and claims it before spawning the child. Failed/unknown dispatch blocks the claimed node; cancellation and interrupted session restoration fail closed with a structured Blocker. A returned TaskResult changes `running` to `result_available` and remains in the Operation, not the graph. Rejection returns the TaskOrder to `ready` only with budget left; otherwise it becomes `exhausted`. Acceptance validates the verified TaskResult first, then updates Operation and TaskGraph in memory together and recalculates dependents. A combined session entry persists both. An Operation still requires all accepted TaskResults **and** its own explicitly judged Acceptance Criteria. Completion never changes Mission status.

`Commander -> Coordinator -> Harness Scheduler -> ready TaskOrder -> ExecutionUnit -> Verifier -> TaskResult -> Scheduler / Operation -> OperationReport -> Commander`. Execution remains serial (`.pi/subagents.json` maxConcurrent 1); even if two IDs are ready, the Coordinator selects one. A session switch aborts old managed/direct child work and an epoch guard prevents old TaskResults from mutating the new session's TaskGraph. Compaction checkpoints Mission, Operation, CoordinatorState, TaskGraph and proactive policy but does not itself dispatch, accept, reject, retry, block or exhaust any TaskOrder. A normal reload of an interrupted running claim is the separate, explicit safety reconciliation; compaction does not reconcile it. A legacy Phase E session without a TaskGraph entry migrates its Operation and bounded `dispatch_counts` into Scheduler attempts once, then writes the canonical combined snapshot. Later CoordinatorState omits these counts.

**Not yet shipped:** domain Heads, dynamic TaskGraph expansion, parallel Worker execution, resource-aware scheduling, model-aware routing, security-reviewer routing, persistent cross-session project intelligence, or automatic Mission acceptance.

## Future coordination beyond Phase E

**Manual compatibility flow:** Main Pi may still call `pi_harness_coordinate(owner, scope, verification, permission, model?, task_id?, operation_id?, constraints?, acceptance_criteria?, review_evidence?)`. Harness alone may dispatch a read-only `reviewer` when semantic criteria remain. Harness validates the three allowed owners, builds a prompt, requests a background child through the pi-subagents RPC event bus, waits for its terminal event and returns JSON. Scout/research have read-only tools and no worktree; their `verification` is prompt text, not an executed gate. Worker uses package-managed worktree and commit; Harness runs the shell gate in that worktree before cleanup, checks commit count/message and returns a branch for separate integration. Group-scoped abort signals link active tasks to `/goal cancel`; the TaskGraph and serial Scheduler persist Operation Dependency and retry state; a separate Coordinator context exists only for managed Operations. Worker `success` combines terminal status, gate and commit policy, not mission acceptance. The direct internal execution record retains bounded child result text (up to 8 KB), gate output (8 KB) and diff (20 KB). The parent tool result now contains only the versioned TaskResult. The Harness Evidence Store persists bounded raw execution data and offers internal integrity-checked retrieval; the parent sees only references. Compaction saves goal/plan and supplied decision/file/gate summaries, not persistent project intelligence. `/learn` is user-written reference memory, not a scout cache.

**Minimum contract:** Main Pi is commander (L0 objective, constraints, decisions, DoD, status). Coordinator is a separate L1 context for managed Operations (main Pi retains manual compatibility tools) (operation plan, dependencies, concise results, retry/escalation). Optional heads may propose orders, never own spawn or cancellation. An L2 TaskOrder needs an objective and bounded scope, relevant context/constraints, role profile and permission, acceptance criteria, deliverables, verification, reporting limit; IDs/dependencies when coordinating several tasks. The current API enforces a minimum subset: role (legacy `owner`), objective/scope (legacy `scope`), permission, verification, optional ID, Constraints and Acceptance Criteria. The rest is doctrine, not an enforced schema. Scout, research, implementation, testing and review are role/capability profiles of an ExecutionUnit, not new process primitives; scout/research/worker and the Harness-only reviewer profile exist today. No recursive fanout. Harness owns routing/policy, gate/result normalization, task status and cancellation linkage; pi-subagents owns child lifecycle, concurrency and worktree isolation. Pi owns model/provider/session/compaction. The L3 ExecutionUnit performs disposable work. The Verifier checks TaskOrder Acceptance Criteria with deterministic gates first and a reviewer only when needed. The Coordinator judges Operation Acceptance Criteria using explicit Evidence references; this is not independent semantic verification. Persistent project intelligence, if built, should be replaceable Harness-owned state outside the repository; task-specific reconnaissance stays ephemeral.

**Promotion:** execution record (private evidence/artifacts) to TaskResult (ID, status, summary, changed paths, verification, evidence/artifact references and surprises) to L1 operational summary to L0 mission status. A package child terminating is `execution_complete`, not `verified`: accept only after criteria are checked; otherwise retry, block or fail. No raw logs/diffs/transcripts promoted by default. Preserve worker isolation, one package-managed commit, explicit user-approved integration and central cancellation. Harness enforces result filtering, deterministic and bounded semantic verification, and explicit Coordinator Operation acceptance; it does not auto-complete a Mission.

## Skills and ownership

`skills/skills.lock.json` is the self-contained package manifest: it lists each registered skill and hashes every file shipped with it. `npm run verify:skills` checks the exact skill-directory inventory and file contents without consulting another repository, Git commit, remote, or private workspace. Pi Harness owns every skill under `skills/`; promoted public skills have no active upstream ownership dependency. New skills require explicit review, package allowlisting, and lock updates.

## ACP and external presentation

`packages/pi-harness-acp` is the active ACP owner. It exposes ACP over stdio, owns the Pi RPC session process and session mapping, translates Pi events, relays cancellation, and projects `/plan`, `/goal`, `/learn`, and `/skill-hub`. The bridge has no ACP runtime dependency; upstream `pi-acp@0.0.33` is not an active dependency because it does not expose the required extension-command projection hook.

TUI-specific status is optional; ACP clients receive textual command/status data. The package has no browser or screen-reader claim. Zed registration and end-to-end ACP forwarding require their dedicated smoke tests before release.

## Native feature boundaries

- Provider, model, authentication, local model servers, session tree, and compaction remain Pi-owned.
- Memory writes occur only through explicit `/learn`; storage is bounded and private, with no autonomous write tool.
- Precise editing is `pi_harness_hashlines` plus `pi_harness_patch` under the small SHA/range contract.
- Web is a lightweight CLI using Brave or DuckDuckGo search, direct public HTTP(S), and bounded Jina fallback after private/local validation, with 10-second timeouts and a 1 MB body cap.
- Skills are loaded from the locally canonical package set and verified against per-file checksums in the package lock.

## Security boundaries

- Web lookup receives only a task query or URL, with timeout and response-size cap.
- No credentials, provider configuration, or workspace contents are sent by doctor or the web CLI.
- Bootstrap contains no secret and creates no shell alias or wrapper.
