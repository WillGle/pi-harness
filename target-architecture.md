# Pi Harness Architecture

## Scope

Pi Harness is a Pi package for Pi `0.87.1`; it does not replace Pi, select a provider/model, create a separate GUI, or train a model. Provider, model, and authentication remain machine-local Pi choices.

## Package layout

```text
pi-harness/
├── extensions/pi-harness.ts       # Harness commands and tools
├── lib/state.mjs                  # persisted-state and safety contracts
├── lib/coordinator.mjs            # Harness-only pi-subagents dispatch adapter
├── lib/operation-runner.mjs       # bounded Coordinator state and bounded Coordinator control loop
├── lib/task-graph.mjs             # persistent TaskGraph and deterministic Scheduler
├── lib/communication.mjs          # L2 TaskOrder/TaskResult contract and promotion
├── lib/evidence.mjs               # local bounded Evidence Store and integrity-checked retrieval
├── lib/verifier.mjs               # Harness-owned deterministic acceptance checks
├── lib/semantic-verifier.mjs      # bounded VerificationOrder and checked semantic result
├── lib/operation.mjs              # session-scoped Coordinator acceptance state
├── lib/worker-gate.mjs            # Harness-specific verification and result policy
├── lib/memory.mjs                 # explicit /learn project memory
├── lib/precise-edit.mjs           # bounded hashline editing
├── lib/code-intel.mjs             # bounded code intelligence
├── bin/pi-harness*.mjs            # doctor and bounded web CLI
├── skills/                        # curated, locked Pi skills
└── packages/pi-harness-acp/       # ACP stdio bridge
```

`package.json` declares Pi extensions, skills, executable commands, and the pinned `@tintinweb/pi-subagents@0.19.0` dependency. It has no project prompt resource. `.pi/subagents.json` sets background `maxConcurrent: 4`, foreground `maxConcurrentForeground: 1`, and explicit worktree isolation; Harness owns the stricter active Task pipeline limit. `scripts/bootstrap.mjs` checks Node/Pi and installs this package through `pi install`; it must not modify Pi provider, model, or authentication settings.

## Session behavior

The extension persists `pi-harness-plan-state`, `pi-harness-goal-state`, `pi-harness-operation-state`, `pi-harness-coordinator-state`, and `pi-harness-task-graph-state` custom session entries. The newest TaskGraph entry includes its owning Operations as one atomic Scheduler snapshot; it takes precedence over older legacy Operation entries during restore. It also checkpoints before Pi-native compaction and deterministic context maintenance. Session reload reconciles an interrupted `running` claim into an explicit Scheduler Blocker, never a ghost running Task. The model does not own this state.

- `/plan on` removes `edit` and `write` from active tools. In plan mode, bash is limited to classified read-only commands and the agent receives a planning prompt requiring assumptions, numbered steps, and verification criteria.
- `/plan off` restores tools captured before plan mode. `/plan status` reports state.
- `/goal <objective>` creates one active goal only when plan mode is off. `/goal status` reports it; `/goal cancel` records cancellation. Terminal completion/blocking must carry evidence.

The current implementation persists and enforces these command contracts. The lifecycle tests prove persisted reload, real compaction, real fork/branch independence, and mutation blocking after lifecycle transitions. The goal intentionally does not own wait state, pause/resume, token budgets, or a strong no-progress circuit breaker.

## Coordination boundary

Every delegated task needs an owner, scope, verification command, and permission. `@tintinweb/pi-subagents` owns child sessions, tool restrictions, queues, concurrency, cancellation, and worktrees. Harness agent definitions keep scouts/researchers read-only and workers write-capable. Harness runs the worker gate and commit policy, captures bounded evidence, links goal cancellation, and leaves branch integration as a separate, explicit user-confirmed action. No worker may edit the coordinator worktree.

## Communication contract (Harness-enforced control-plane foundation)

Canonical control-plane language is **ASD-STE100-derived Agent English**. This uses ASD-STE100 principles only; no certified ASD-STE100 compliance or full parser is claimed. Compress redundancy, not control semantics. Use one term per concept and one meaning per term. Use short sentences, one main fact per sentence, active voice when practical and an explicit actor. Put conditions before dependent actions. Preserve `if`, `only if`, `unless`, `before`, `after`, `because`, `while`, `until`, `must`, `must not`, `may`, `cannot`, `requires`, `depends on`, negation and exceptions. Keep identifiers exact. State uncertainty and status explicitly. Do not infer verification from execution completion.

| Layer | Contract |
|---|---|
| L0 Commander | Controlled Technical English. The Harness injects this policy in the Commander context. L0 receives Mission, Constraints, Definition of Done, important Decisions, major Blockers, Mission status, and bounded OperationReports. It does not receive TaskResults or raw L3 context. |
| L1 Coordinator | Concise Controlled Technical English. The Harness includes the same policy in every Coordinator turn and agent profile. L1 receives bounded Operation and TaskOrder state, Dependencies, TaskResults, retry/replan decisions, escalation and Blockers. L1 does not receive raw Evidence, logs, diffs, shell output, or Worker transcripts. |
| L2 TaskOrder / TaskResult | Versioned schema plus Controlled Technical English in semantic text. Harness formats TaskOrders and projects TaskResults before they enter L1. A read-only TaskOrder in an Operation requires an Acceptance Criterion; the Verifier converts its raw report into structured, evidence-backed Findings before promotion. |
| L3 Worker / ExecutionUnit | Normal technical language. Source, debugging, commands, retries and raw test output are disposable and do not automatically propagate. The Harness does not force Controlled Technical English during implementation. |
| Evidence / Artifact | Harness stores bounded raw execution data outside the repository. TaskResult carries references only. The Verifier reads selected Evidence. Storage does not rewrite or language-compress its bytes. A worker branch remains an Artifact, not Evidence. |
| Caveman | Optional human-requested presentation or L3 compact execution receipt only. A receipt is not a TaskResult. It cannot rewrite L0/L1/L2 semantics. |

Canonical terms: Mission (L0 objective), Operation (coordinated work), TaskOrder (dispatch contract), TaskResult (promoted semantic result), ExecutionUnit (package child), Commander (L0 decision maker), Coordinator (L1 decision maker), Worker (write-capable execution profile), Verifier (acceptance checker), Constraint (limit), Acceptance Criterion (required check), Dependency (required prior state), Blocker (blocked action and condition needed to resume), Evidence (raw observation), Artifact (produced output), Execution Status (execution lifecycle), Verification Status (acceptance checks). Avoid synonyms such as job, ticket, assignment, work item, request and work order for TaskOrder.

Status vocabulary: `assigned` means the Coordinator assigned the TaskOrder; `running` means the ExecutionUnit is executing it; `execution_complete` means normal termination with an execution result, **not** verification; `verifying` means the Verifier is checking Acceptance Criteria; `verified` means all required Acceptance Criteria passed; `failed` means execution or verification failed; `blocked` means a stated Blocker prevents progress; `complete` means the parent Operation accepted its required verified TaskResults and Operation Acceptance Criteria. `not_verified` means no complete acceptance check has occurred. Do not interchange these statuses. While a managed Task pipeline runs verification, TaskGraph persists `verification_status: verifying` without changing Scheduler or Execution Status. Harness removes that transient field when it records the final TaskResult, which carries the final Verification Status. If the Worker passes all deterministic checks and Evidence persistence succeeds, the Verifier returns `verified` unless semantic Acceptance Criteria remain. Read-only Operation TaskOrders always have explicit Acceptance Criteria and are promoted only after the Verifier checks the report. The legacy `success` property in internal records is not a Verification Status.

TaskOrder v1 keeps the flat compatibility fields, generates an ID when absent, and formats the explicit actor, objective, Constraints, Acceptance Criteria and verification without paraphrasing caller text. Every managed read-only TaskOrder requires at least one Acceptance Criterion. TaskResult v1 contains separate Execution Status and Verification Status, a Harness-generated summary, changed paths, Artifact references, Evidence references, and structured Findings when verification passes. The Verifier checks raw read-only reports against the exact Acceptance Criteria. It promotes only structured Findings with Evidence references; it does not promote child prose. The Commander receives only an OperationReport. The legacy `pi_harness_coordinate` tool is a disabled compatibility stub; it cannot spawn or return a TaskResult. `pi_harness_operation` can create an Operation or return a safe status projection. Only the Harness Coordinator can dispatch, accept, reject, or judge TaskResults in an Operation. If Evidence persistence fails, the TaskResult cannot be `verified`. Caveman and Cavecrew do not own dispatch or state. Pi owns provider/model/session/compaction and pi-subagents owns child lifecycle/worktrees. Harness owns deterministic Context GC, not lossy compaction. `/harness-compact set <50-90>|status|disable` retains its compatibility name but configures a soft maintenance threshold (default 70%). At `turn_end` or `agent_before_settle`, with no active tool, child, Operation or pending message, Harness checkpoints state and returns native ContextEdit drafts. Exact legacy contracts and accepted execution/status representations superseded by a later complete OperationReport can shrink; active/current-turn and unresolved state remain. Raw session history is retained. Harness never calls `ctx.compact()`. Pi owns reserve/window safety and actual compaction; `session_before_compact` checkpoints without scheduling. One maintenance attempt per high-water mark prevents repeated loops. Stable communication/memory/plan content uses Pi-native system prompt sections, not accumulating conversation entries. Native cache warming is suppressed only for maintenance, prefix invalidation, compaction or session end; Harness never sends keepalive prompts. `/harness-context` reports available token/cache metrics, GC bytes and native edit/compaction counts; unavailable values are null and catalog-derived cost is not provider-reported billing. The control contract is enforced by Harness code and prompts, not optional skill selection. No ASD-STE100 parser or certification is claimed.

## Shipped Evidence and Verifier pipeline

`Commander -> Coordinator -> TaskOrder -> ExecutionUnit -> Evidence Store -> deterministic/semantic Verifier -> TaskResult -> Coordinator decision -> Operation -> OperationReport -> Commander evaluates Mission Definition of Done`. Operation `complete` does not set Mission `complete`. Harness stores bounded raw Worker execution result, gate output, diff, and read-only report as Evidence. The Verifier checks selected Evidence against Acceptance Criteria. Only the semantic TaskResult and checked Findings enter the Coordinator context. The parent receives only the bounded OperationReport, never raw Evidence or an individual TaskResult. The Verifier evaluates captured gate and package commit checks after execution; it never accepts a Worker claim or legacy `success` as authority.

The file-backed Evidence Store defaults to `~/.pi-harness/evidence/<project-identity>/`, separately from `/learn` memory. `PI_HARNESS_EVIDENCE_DIR` overrides the absolute store root. An Evidence reference has the form `evidence://<project-identity>/<opaque-UUID>`; a caller-supplied TaskOrder ID never becomes a path component. The internal `readEvidence(reference, cwd)` API checks project identity, regular-file ownership/mode, reference grammar, byte limit and SHA-256 before returning bytes. Storage records TaskOrder ID, kind, byte count, SHA-256, creation time and truncation state in a private metadata file. Created directories use owner-only mode; existing store/project directories must be private. Evidence files use owner-only mode, exclusive creation and no-follow flags; directory symlinks are rejected. The implementation does not include a model-facing retrieval tool. Harness explicitly retrieves selected Evidence for semantic review; it does not supply Evidence Store paths to the Reviewer.

Storage preserves the bytes it receives. The existing bounded capture may already append a visible truncation marker; metadata records that truncation. The synchronous gate capture concatenates stdout and stderr without trimming them. It cannot preserve the interleaving of the two streams. Capture limits remain 8 KB for result/gate and 20 KB for diff; storage also has a 32 KB per-item cap. There is no automated retention or quota across tasks. Local users must manage Evidence retention. Evidence is not encrypted or remotely served. A persistence failure produces no fabricated reference and prevents `verified`; references for items successfully stored before a partial failure may remain. Pi still owns provider/model/session/compaction. Pi-subagents still owns child lifecycle/worktrees. Harness does not auto-integrate branches.

### Semantic Verification and Operation acceptance

If a Worker passes deterministic checks and the TaskOrder has additional semantic Acceptance Criteria, Harness sends a bounded VerificationOrder to the read-only `reviewer` ExecutionUnit. Only four exact Worker criteria are classified as already machine-checked: `The Worker verification command passes.`, `The package-managed branch exists.`, `The Worker commit policy is valid.`, and `The Worker produced exactly one commit.` Unknown text remains semantic; there is no natural-language classifier. Every read-only Operation TaskOrder must include at least one explicit Acceptance Criterion. The semantic Verifier checks its exact criterion text against the raw report and returns structured findings in Controlled Technical English. Harness validates the result and evidence references before it can enter the TaskResult. The packet contains exact criterion text, objective, Constraints, changed paths, and selected raw Evidence. A TaskOrder can select an Evidence kind per criterion; Harness validates the kind, integrity, truncation, and 24 KB packet limit. Harness never sends a Worker transcript or unrelated Evidence. The Verifier cannot mutate the repository, spawn children, accept an Operation, or override deterministic or Evidence failure. A `Finding` has a criterion statement, source role, Verification Status, and selected Evidence references; only verified Findings enter the OperationReport. Semantic judgment is not a formal proof or an ASD-STE100 validator.

`pi_harness_operation` creates a session-persisted Operation with an objective, registered TaskOrder IDs, optional Dependencies and Operation Acceptance Criteria. It exposes only `create` and a Commander-safe `status` projection. The Commander calls `pi_harness_run_operation`; the separate Coordinator proposes `accept_task`, `reject_task`, or `accept_criterion` decisions. Harness alone applies those decisions after checking the TaskResult Verification Status, Dependencies, and Evidence. Public tools cannot accept or reject a TaskResult. The Operation becomes `complete` only after all required TaskResults and Operation Acceptance Criteria are accepted. Its status is not Mission status. Operation-level criterion judgments remain Coordinator decisions, not independent semantic proofs. Session entries store Operation state with the TaskGraph. No direct compatibility tool can bypass the Scheduler or promote a TaskResult to the Commander.

**Not shipped:** dynamic TaskGraph expansion, dynamic refill during an active Task wave, Mission-level automatic acceptance, or project intelligence. The Reviewer runs as a package-managed sibling, never as a recursive child.

### Separate Coordinator context (Phase E)

The Commander hands a registered Operation to `pi_harness_run_operation({ operation_id, model? })`. The parent receives only a versioned OperationReport (`operation_id`, `status`, concise summary, accepted/blocked TaskOrder IDs, at most five verified Findings, Blocker, optional strategic escalation, and `commander_action_required`). The report is capped at 24 KB, dropping Findings before exceeding the cap. It does not receive individual TaskResults or Coordinator/Worker/Verifier transcripts. The legacy `pi_harness_coordinate` tool is disabled. `pi_harness_operation` never returns TaskResults or Evidence references. Operation completion never calls `/goal complete`.

Harness builds an OperationBrief v1 from Operation objective, optional current Mission objective, Scheduler ready/pending/running/result_available/accepted/blocked/exhausted TaskOrder IDs, Dependencies, Operation Acceptance Criteria, and semantic TaskResults. CoordinatorState v1 records only the Operation ID, turn count, last seven concise Decisions, and Blocker. Retry accounting belongs to the TaskGraph, not CoordinatorState. A 16 KB packet cap rejects oversized state. The Coordinator profile `.pi/agents/coordinator.md` has only `read` as a built-in tool; `extensions: false`, `skills: false`, `prompt_mode: replace`. Pi-subagents 0.19.0 parses an omitted `tools:` field as **all built-ins**, but parses `tools: none` as zero built-ins. The Coordinator declares only `read` and is instructed not to read files in normal coordination. The profile never receives Evidence Store paths or main session messages.

The Coordinator returns one JSON CoordinatorDecision v1 per turn: `dispatch`, `dispatch_batch`, `accept_task`, `reject_task`, `accept_criterion`, `block`, or `report`. Harness checks version, Operation ID, fields, TaskOrder registration, Dependencies, read/write permission, task verification, Evidence refs from accepted TaskResults, and state transitions. A Coordinator Decision cannot invoke tools or spawn a Worker. Harness claims one TaskOrder or an independent Task wave before spawn. It persists each TaskResult separately; the next Coordinator turn starts only after the wave settles. The Coordinator cannot mark Mission complete or integrate a branch. A strategic `block` states the blocked action and required condition; an optional question becomes a structured `strategic_decision_required` escalation. Routine retry remains inside L1. Each TaskOrder has at most two recorded attempts; a run has at most 12 Coordinator turns. Invalid output, exhausted retries, no executable action, or cancellation returns a blocked OperationReport, not success.

**Coordinator session experiment:** the installed pi-subagents 0.19.0 `spawnTopLevel` removes `resumeSessionFile` from RPC options. Only its internal `@handle` dispatcher may resume a stored child session. Harness cannot safely resume a completed Coordinator via RPC, so it uses bounded CoordinatorState and fresh Coordinator turns. Each Coordinator turn terminates before a Task wave is spawned; its package slot is released. The test checks the installed package's RPC sanitizer; Harness does not replay a Coordinator transcript. Session entries restore Operation and Coordinator state on reload; switching sessions aborts an active run and prevents it from persisting into the new session. Goal cancellation aborts the active Coordinator turn or managed Worker/Reviewer through its run signal; `pi_harness_cancel_operation` aborts one active managed run. Other Operation state remains unchanged.

### Persistent TaskGraph (Phase F) and bounded parallel Task waves (Phase H — SHIPPED)

`TaskGraph` v1 has `operation_id` and `nodes` keyed by registered TaskOrder ID. Each node stores `task_id`, normalized Dependencies copied from the owning Operation, exact `scheduler_status`, `attempts`, `max_attempts` (2), and an optional structured Blocker (`task_id`, `blocked_action`, `required_condition`). While `scheduler_status` is `running`, it may store `verification_status: not_verified | verifying`; Harness removes this transient field when the TaskResult is recorded. The graph stores no TaskResult, raw Evidence, Worker/Verifier transcript, stdout, or diff. The Operation owns accepted Task IDs and TaskResults; every graph validation checks exact accepted-set agreement. Graph creation rejects missing, duplicate, and self Dependencies and uses depth-first visiting/visited sets to reject cycles of any length before the Operation is persisted. No Task IDs or Dependencies can be added or rewritten while it runs.

**Scheduler Status** is distinct from Execution Status, Verification Status and Operation status: `pending` (Dependency not accepted), `ready` (all Dependencies accepted with retry budget), `running` (claimed attempt persisted before spawn), `result_available` (TaskResult recorded; Coordinator must decide), `accepted` (verified TaskResult explicitly accepted), `blocked` (structured Blocker prevents dispatch), and `exhausted` (rejected attempt used the last retry). `verifying_task_ids` identifies running TaskOrders whose Verifier is checking Acceptance Criteria; it does not change Scheduler Status. `readyTaskIds` requires an open Operation, accepted Dependencies, an eligible ready node and remaining attempt budget. A running sibling does not make an independent Task non-ready. `parallel_limit` and `available_slots` govern dispatch capacity, not readiness. The Coordinator receives bounded Scheduler summary IDs and capacity, selects a ready TaskOrder or batch, and cannot mutate readiness. Harness validates the selection and persists its claim before spawning any child. Failed/unknown dispatch blocks the claimed node; cancellation and interrupted session restoration fail closed with a structured Blocker. A returned TaskResult changes `running` to `result_available` and remains in the Operation, not the graph. Rejection returns the TaskOrder to `ready` only with budget left; otherwise it becomes `exhausted`. Only the Coordinator may accept a verified TaskResult or Operation Acceptance Criterion. Acceptance validates Dependencies and Evidence before Harness updates Operation and TaskGraph in memory together and recalculates dependents. A combined session entry persists both. An Operation still requires all accepted TaskResults **and** its own explicitly judged Acceptance Criteria. Completion never changes Mission status.

`Commander -> Coordinator -> Harness Scheduler -> ready TaskOrder -> ExecutionUnit -> Verifier -> TaskResult -> Scheduler / Operation -> OperationReport -> Commander`. Phase H permits concurrent independent ready Tasks inside one managed Operation. `ready` expresses Dependency acceptance and retry budget, not slot capacity. The Harness claims all selected IDs in one validated, persisted TaskGraph snapshot before spawning any child. TaskGraph v1 can contain several `running` nodes; each completion persists its own TaskResult and `result_available` transition while siblings remain running. The next Coordinator turn waits for all wave pipelines to settle. Package background capacity is 4; the Harness default is 2 active Task pipelines (maximum 4). A session switch aborts old managed/direct child work and an epoch guard prevents old TaskResults from mutating the new session's TaskGraph. Compaction checkpoints Mission, Operation, CoordinatorState, TaskGraph and context maintenance policy but does not itself dispatch, accept, reject, retry, block or exhaust any TaskOrder. A normal reload of an interrupted running claim is the separate, explicit safety reconciliation; compaction does not reconcile it. A legacy Phase E session without a TaskGraph entry migrates its Operation and bounded `dispatch_counts` into Scheduler attempts once, then writes the canonical combined snapshot. Later CoordinatorState omits these counts.

**Not yet shipped:** dynamic TaskGraph expansion, dynamic refill within an active wave, resource-aware scheduling, arbitrary model-aware routing, automatic security classification, persistent cross-session project intelligence, or automatic Mission acceptance.

### Parallel Task waves (Phase H — SHIPPED)

One managed Operation may issue `dispatch_batch` with 2–4 distinct registered ready TaskOrders. Harness validates the entire decision, accepted Dependencies, retry budgets and available slots, then increments attempts and marks all selected nodes `running` in one TaskGraph snapshot before any spawn. `dispatch` remains the single-Task path. The bounded OperationBrief contains ordered Scheduler IDs, `parallel_limit` and `available_slots`; no transcript or worktree path enters it. The Coordinator and Heads remain serial and advisory. `PI_HARNESS_MAX_PARALLEL_TASKS` is read once at Harness initialization: unset means 2; only integer strings 1–4 are valid; invalid values fail initialization. `.pi/subagents.json` permits four background children and one foreground child; package queue state is not Scheduler truth.

Harness starts claimed Task pipelines with `Promise.allSettled`. Synchronous per-completion transitions persist each TaskResult and Scheduler snapshot immediately; completion order cannot reorder OperationBrief TaskResult keys, which follow `required_task_ids`. Each Task owns its Worker worktree, Evidence, general Reviewer or security-reviewer, and verification status. Distinct workers may modify the same path in separate branches; branch merge compatibility is NOT verified and Harness never integrates automatically. A rejected dispatch or unknown child outcome blocks only that Task without refunding its attempt; healthy siblings continue. If the atomic claim cannot persist, no child starts. Retry stays per Task, maximum two attempts. A dependent Task becomes ready only after the Coordinator explicitly accepts every Dependency, not when a sibling finishes or becomes verified.

Goal or managed Operation cancellation aborts every active Task pipeline in the wave through its group signal. Unknown outcomes become blocked; known, persisted TaskResults remain available. A session switch aborts old children, and the epoch guard prevents old snapshots from entering the new session. Restore reconciliation blocks every unresolved `running` node. Proactive compaction waits until the whole wave and all active child work settle; it never changes TaskGraph state. The Coordinator waits for the entire wave before another decision. Dynamic refill while siblings remain active, concurrent managed Operations, automatic branch integration, conflict resolution, resource-aware or CPU/RAM/GPU/provider-quota scheduling, distributed execution, dynamic TaskGraph expansion, arbitrary-domain routing and Mission auto-completion remain NOT SHIPPED.

### Security capability (Phase G.1 — SHIPPED)

`/skill:security` is a packaged, locked Pi skill with `disable-model-invocation: true`. It guides defensive code and architecture reasoning only. **Security skill != security-reviewer. Security Head != security-reviewer. Invoking the security skill does not select Daybreak.** Only explicit security Verification Criteria route to `security-reviewer`. No natural-language classifier exists. A Head can recommend a TaskOrder with `review_profile` but cannot spawn a Verifier or issue `verified`.

A TaskOrder can specify `review_profile: { "exact criterion": "default" | "security" }`, independently of `review_evidence`. Keys must match Acceptance Criteria exactly. Missing entries select `default`; duplicate Acceptance Criteria, foreign keys, unknown profiles, and more than 32 entries are rejected. Deterministic criteria do not need a profile. After deterministic verification, Harness partitions remaining criteria by profile, runs the general Reviewer for default criteria and the read-only `.pi/agents/security-reviewer.md` for security criteria, then joins exact per-criterion results. All must pass. Deterministic execution, gate, branch, commit, and Evidence failures take precedence; a security pass cannot override another failure.

The security VerificationOrder uses the existing 24 KB packet: Task ID, exact selected criteria, objective, constraints, changed paths, selected Evidence content and references. No transcript or Evidence Store path enters the packet. The security reviewer declares `tools: none`, with `extensions: false`, `skills: false`, `prompt_mode: replace`. Pi-subagents 0.19.0 treats an omitted `tools:` field as all built-ins; the explicit `tools: none` grants zero built-ins in the installed parser. The prompt also prohibits tool use and file browsing. It cannot mutate, spawn, accept an Operation, or complete a Mission. Raw bounded output is stored as `security_review` Evidence, not in control summaries. The TaskResult includes bounded criterion findings, Evidence references, and `verifier: security` provenance; only passed findings with references can be promoted as verified facts. Harness retains acceptance authority. Cancellation and session epoch guards use the existing managed group lifecycle. Active review prevents Harness context edits; no raw review output enters the checkpoint.

Harness requests `openai/gpt-daybreak-blue-latest` **only** for the security-reviewer RPC model override. `PI_HARNESS_SECURITY_REVIEW_MODEL` can select a bounded `provider/model` identifier locally; TaskOrders cannot choose this model. Harness checks the exact model in Pi's available-model snapshot before sending Evidence and checks the actual invocation model after completion. If Pi/provider does not expose the exact model, access is not provisioned, or the child fails, verification is `blocked`; there is no normal Reviewer fallback. Pi owns authentication and provider configuration. The model may require a separate Daybreak access program; selecting an identifier does not grant access. The pi-subagents 0.19.0 RPC accepts `options.model` and resolves it through Pi; its runner also accepts `options.thinkingLevel`, but Harness does not set it because model-specific support has not been established. Neither an `xhigh` override nor a global thinking change is required.

NOT SHIPPED: automatic security criterion classification, arbitrary domain model routing, Daybreak Red, offensive-specialist routing, dynamic TaskGraph expansion, resource-aware scheduling, persistent project intelligence.

### Optional Domain Heads (Phase G — SHIPPED)

An Operation can register zero or more static Heads at creation with `heads: [{ head_id, domain, task_ids }]`. It can also provide shared bounded `constraints` and optional bounded `task_intents` keyed by registered Task ID. An intent is setup context, not a TaskOrder or a Scheduler node. The versioned Head Registry belongs to the Harness, not the TaskGraph. Each Head has a unique bounded nonempty ID and domain and at least one assigned Task ID. An assigned ID must exist and can belong to only one Head; unassigned Tasks are valid. Runtime Head creation, removal, and reassignment are NOT SHIPPED.

The Coordinator can return `consult_head` with a registered `head_id`. Harness builds a bounded DomainBrief v1 (12 KB maximum) with the actual Operation objective, assigned Task IDs and their available intents, shared Operation constraints and Acceptance Criteria, Scheduler status IDs in that slice, Dependency IDs with accepted/pending status only, and semantic TaskResults for assigned Tasks. It does not include unrelated TaskResults, transcripts, raw Evidence, diff, stdout, stderr, or Commander history. Harness sends one fresh turn to `.pi/agents/head.md` with `extensions: false`, `skills: false`, `prompt_mode: replace` and only the `read` built-in (the narrowest safe pi-subagents 0.19.0 tool declaration). The Head must not use tools. The Head cannot spawn or call Harness tools. Its JSON HeadDecision v1 can recommend dispatch, acceptance, rejection, block with a required condition, or report. Harness rejects foreign IDs, invalid fields, and dispatch of a Task outside the Scheduler ready set. The validated HeadReport v1 contains the action, optional Task ID, concise reason, optional structured Blocker, and, for `recommend_dispatch`, the bounded proposed TaskOrder fields (`task_id`, `owner`, `permission`, `scope`, `verification`, optional `constraints`, `acceptance_criteria`, `review_evidence`, and `review_profile`). The Coordinator receives the proposal but Harness does not dispatch it. It is advice: it changes no Scheduler, TaskResult, Verification, Operation, or Mission state. The Coordinator must issue a later validated decision; only Harness executes it. A security Head is not a security Reviewer.

HeadState v1 stores only Operation/Head IDs, turn count, last three concise decisions, and optional Blocker. Dedicated session entries persist registry and state and restore them on reload. The compaction checkpoint includes both entries without consulting a Head. The Coordinator stores a bounded consultation count; after three consultations without a dispatch or acceptance/rejection transition, Harness returns a Blocker. Goal/Operation cancellation aborts the active Head turn through the managed run signal. An epoch guard prevents an old Head result from changing a new session. Cross-domain Dependencies expose only accepted/pending status to the dependent Head. Scheduler readiness and Operation acceptance remain authoritative. Operations without Heads follow the Phase F path. Dynamic refill during a wave, dynamic TaskGraph expansion, resource-aware scheduling, automatic model routing for arbitrary domains and persistent project intelligence are NOT SHIPPED.

## Communication contract result and remaining implementation delta

**Legacy compatibility boundary:** `pi_harness_coordinate` remains registered for a clear migration error but cannot spawn an ExecutionUnit or return a TaskResult. All dispatch flows through a registered Operation and the separate Coordinator. Harness retains bounded raw child output and Evidence internally. The Commander receives the OperationReport, not the raw execution record or TaskResult. Compaction saves goal/plan and supplied decision/file/gate summaries, not Worker transcripts or raw Evidence. `/learn` is user-written reference memory, not a scout cache.

**Minimum contract:** Main Pi is Commander (L0 Mission, Constraints, Definition of Done, Decisions, Blockers, and status). The separate Coordinator owns L1 Operation state and every TaskResult transition. An L2 TaskOrder has a structured actor/role, objective, scope, permission, Constraints, Acceptance Criteria and verification. The current flat TaskOrder API remains internal to the Harness; the Commander cannot dispatch it directly. Every read-only TaskOrder in an Operation has a checkable Acceptance Criterion. Harness owns prompts, schema validation, semantic normalization, Verification Status, Operation acceptance and cancellation linkage; pi-subagents owns child lifecycle, concurrency and worktree isolation. Pi owns model/provider/session/compaction. The L3 ExecutionUnit uses normal technical language and remains disposable. The Verifier reads selected raw Evidence and promotes only validated structured Findings. Persistent project intelligence remains unimplemented and separate from compaction and `/learn` memory.

**Promotion:** raw execution stays in private Evidence/Artifacts. The Verifier checks TaskOrder Acceptance Criteria and creates a versioned TaskResult with distinct Execution Status and Verification Status, a Harness-generated summary, exact changed paths, Evidence/Artifact references, and structured Findings only when Evidence supports them. The Coordinator receives the TaskResult. The Commander receives only the bounded OperationReport. A package child terminating is `execution_complete`, not `verified`; the Coordinator may accept only after the Verifier marks the TaskResult `verified`. No raw logs, diffs, or transcripts are promoted by default. Harness enforces status separation, evidence-backed normalization, Coordinator-only Operation acceptance, and Mission/Operation separation. It does not auto-complete a Mission.

## Skills and ownership

`skills/skills.lock.json` is the self-contained package manifest: it lists each registered skill and hashes every file shipped with it. `npm run verify:skills` checks the exact skill-directory inventory and file contents without consulting another repository, Git commit, remote, or private workspace. Pi Harness owns every skill under `skills/`; promoted public skills have no active upstream ownership dependency. New skills require explicit review, package allowlisting, and lock updates.

## ACP and external presentation

`packages/pi-harness-acp` is the active ACP owner. It uses `@agentclientprotocol/sdk` 1.5.0 and targets ACP v1 over stdio. It owns Pi RPC session mapping, translates Pi text/thought/tool events, relays cancellation, and advertises `/plan`, `/goal`, `/learn`, and `/skill-hub`. The upstream `pi-acp@0.0.33` package is not an active dependency because it does not expose the required extension-command projection hook.

The bridge rejects MCP servers and does not advertise `loadSession` or model selection. Pi owns provider, model, and authentication configuration. Automated ACP lifecycle and subprocess tests pass. Zed 0.229.0 GUI prompt integration passed with the registered `pi-harness` agent. This is client integration evidence, not a full official ACP conformance-suite result. See [packages/pi-harness-acp/UPSTREAM.md](packages/pi-harness-acp/UPSTREAM.md) for the tested surface and limits.

## Native feature boundaries

- Provider, model, authentication, local model servers, session tree, and compaction remain Pi-owned.
- Memory writes occur only through explicit `/learn`; storage is bounded and private, with no autonomous write tool.
- Precise editing is `pi_harness_hashlines` plus `pi_harness_patch` under the small SHA/range contract.
- Web is a lightweight CLI using Brave or DuckDuckGo search, direct public HTTP(S), and bounded Jina fallback after private/local validation, with 10-second timeouts and a 1 MB body cap.
- Skills are loaded from the locally canonical package set and verified against per-file checksums in the package lock.

## Security boundaries

- Web lookup receives only a task query or URL, with timeout and response-size cap.
- No credentials, provider configuration, or workspace contents are sent by doctor or the web CLI.
- Bootstrap contains no secret and creates no shell alias or wrapper.

### Harness-owned lifecycle budgets (T1/T2 closure)

The spawn handshake is bounded at 15 seconds (absolute configurable maximum 60 seconds); failure retains a late-reply listener for at most 35 seconds and aborts the exact request signal. Queued children are tracked through the package startup gate; the execution clock starts at RPC acknowledgement and includes remaining queue time. Coordinator, Domain Head, Scout and Research use 120 seconds; a managed Worker uses 300 seconds. No execution budget can exceed 300 seconds. Semantic and Security Reviewers each default independently to 120 seconds.

Worker implementation timing pauses at the package before-cleanup callback. Verification owns a separate 60-second deadline, then cleanup owns 5 seconds. Verification uses an asynchronous shell and parent cancellation signal; timeout/cancel sends TERM to its process group, escalates to KILL after 100 ms, and bounds drain at 1500 ms. Package child settlement/abort drain is bounded at 5 seconds; unknown settlement retains ownership and blocks continuation under the old Task ID. These are sequential phase limits, not a 300-second total-operation limit. Git worktrees and process groups are not an OS sandbox; deliberately escaping process groups is outside the trusted-command boundary.

### Trusted managed TaskSpecs

At Operation registration the Commander/user supplies task_specs keyed by registered Task ID. Harness validates owner, permission, verification, Acceptance Criteria, and review selection centrally. Coordinator dispatches task_id or a bounded task_ids batch; it chooses reasoning and ordering, not shell authority. Legacy full TaskOrder decisions are accepted only when their mechanical fields exactly match the registered spec. Legacy Operations without specs retain historical results but cannot dispatch; replan with registered specs and fresh IDs for blocked/unknown work.

Registered verification commands are explicitly trusted repository/user input executed with host process permissions and environment. Git worktree isolation and process-group cancellation are not an OS sandbox. A semantic Reviewer cannot change registered commands or override deterministic failure.

Git verification/disposition probes use a 5s SIGKILL timeout and bounded buffers. Commander OperationReport findings omit model-authored finding text and raw Evidence references; only verified registered criteria are promoted.
